# 2026-11-20: the app's link stopped working each time TEAM02's IP changed

## What users saw

Anyone following our published link got "This site can't be reached" or a timeout:

- The Deliverable 2 PDF linked `http://149.165.147.165:8000`. That address died the
  same evening, and the PDF had to be reissued with `http://149.165.153.173:8000`.
- `USER_BRIEF.md`, written for the Homework 3 testers and committed Nov 3, still
  linked `http://149.165.147.165:8000`, which had been dead since Oct 28.
- On Nov 20 the address we had been using, `149.165.153.173`, belonged to another
  project's machine. A user following an old link would have reached a stranger's
  server instead of a timeout.

From mid-October to Nov 24, TEAM02's IP changed six times.

## How we found out

Each time ourselves, never from monitoring: a `curl` from a laptop timed out, a
teammate said the link didn't open, or on Nov 20, SSH showed a different host key.

## Timeline (Eastern)

- Before Oct 28: the IP was `149.165.150.147`, kept by choosing "keep IP" when
  shelving, then `149.165.173.215` after an unshelve without it.
- Oct 28, 20:59: the Deliverable 2 PDF goes out with `http://149.165.147.165:8000`.
- Oct 28, evening: the instance is shelved without keeping the IP to save credits.
- Oct 28, about 22:40: unshelved with a new IP, `149.165.153.173`. The PDF is
  reissued at 22:58 and the new link goes to the group chat, but written as the bare
  IP without `:8000`, so the first teammate to try it got "refused to connect".
- Nov 3: `USER_BRIEF.md` is committed with the Oct 28 address.
- Nov 20, about 22:10: before anyone logs in, we check the SSH host key at
  `149.165.153.173`. It is `SHA256:qIkHvUD9…`, not TEAM02's `SHA256:P3MOMLul…`. The
  IP now belongs to someone else. Unshelving gives TEAM02 `149.165.155.182`.
- Nov 20, 22:28: Caddy gets a certificate for
  `team02.cis240466.projects.jetstream-cloud.org` (#51), and the app is served at that
  hostname over HTTPS.
- Nov 20, about 22:55: a shelve and unshelve gives yet another IP,
  `149.165.153.188`. The hostname already points at it, and the site is back a
  minute after boot without anyone logging in.
- Nov 20, 23:14: the docs and the user brief switch to the hostname (#59).
- Nov 24: another unshelve, another IP (`149.165.175.183`); the link keeps working.

## Why it happened

All of these had to be true:

- Jetstream2 releases an instance's floating IP when it is shelved unless "keep IP"
  is chosen, and it is short of IPs, so a released one goes to someone else.
- Several of us shelve TEAM02, as we should to save credits, and the "keep IP"
  checkbox is easy to miss. Our docs said "we keep it when shelving", which
  described a habit rather than something the setup enforced.
- We used the raw `IP:8000` as the app's address everywhere: the PDF, the user
  brief, the docs, the group chat. Jetstream2 already gives every instance a DNS
  name that follows its IP; we didn't use it until we needed one for HTTPS.
- Nothing checked our published links after an unshelve, so stale ones stayed out
  there until someone tried them.

## What went well

- Checking the SSH host key fingerprint before connecting caught that the old IP was
  another machine's, before anyone typed a command or a password there.
- Every container comes back on its own after an unshelve (`restart:
  unless-stopped`), so a new IP was the only thing that broke.
- The diagrams and the PDF are generated by a script, so reissuing the PDF with a new
  address took minutes.

## What we'll change

- [x] Serve the app at the instance's hostname through Caddy, over HTTPS (#51).
- [x] Point the docs and the user brief at the hostname (#59).
- [x] The runbook says to always connect by hostname, gives TEAM02's host key, and
  says never to override a "host key changed" warning (#63).
- [x] Measure it: after a shelve and unshelve with a new IP, the hostname followed
  within a minute (Nov 20, Nov 24), and after `sudo reboot` the site was back in
  about 30 s (#63).
- [ ] Use only the hostname in the final submission, the slides and `discussion.pdf`
  (#60).
